# Task 1.2 — Kueue admits your Job

Kueue is the first upstream controller this platform hands real work to. Before writing a
`TrainingJob` controller that depends on it, drive it by hand: create the queues, submit a plain
`batch/v1` Job, and watch Kueue decide when it may start.

Part one changes no Go code. Part two is the controller, and it is yours.

## What Kueue actually does

Kueue is **not** a scheduler. The kube-scheduler still places pods on nodes. Kueue sits one step
earlier and answers a different question: _may this workload start at all, given what its team has
left of its quota?_

Its lever is one field. A Job created with `spec.suspend: true` has no pods — the Job controller
creates none while suspended. Kueue watches for such Jobs, creates a `Workload` object to represent
the request, decides whether quota is available, and when it is, **flips `spec.suspend` to false**.
That is admission. Everything else — flavors, cohorts, borrowing, preemption — is bookkeeping around
that one decision.

Four objects, in the order they matter:

| Object           | Scope     | Holds                                                        |
| ---------------- | --------- | ------------------------------------------------------------ |
| `ResourceFlavor` | cluster   | a named kind of capacity, usually tied to node labels        |
| `ClusterQueue`   | cluster   | the quota itself: how much of each flavor, and lending rules |
| `LocalQueue`     | namespace | a team's entry point, pointing at one `ClusterQueue`         |
| `Workload`       | namespace | one admission request, created by Kueue, owned by your Job   |

The namespace boundary is the team boundary, which is why `LocalQueue` is namespaced and
`ClusterQueue` is not.

## Step 1 — see what the install gave you

```bash
kubectl get deploy -n kueue-system               # k9s: :deploy kueue-system
kubectl get crd | grep kueue                     # k9s: :crds, then /kueue to filter
kubectl api-resources --api-group=kueue.x-k8s.io
```

You should see `workloads`, `clusterqueues`, `localqueues`, `resourceflavors`, and
`admissionchecks`. The names come back under `kueue.x-k8s.io/v1beta2`, and that is the version every
manifest below uses — the older `v1beta1` is still served but is no longer the storage version. Note
that there are no queues yet: Kueue installs the vocabulary, not the policy. The policy is yours,
which is task 2.3.

## Step 2 — create the smallest possible quota

```bash
kubectl apply -f - <<'YAML'
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata:
  name: default-flavor
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: training
spec:
  namespaceSelector: {}
  resourceGroups:
    - coveredResources: ["cpu", "memory"]
      flavors:
        - name: default-flavor
          resources:
            - name: cpu
              nominalQuota: 2
            - name: memory
              nominalQuota: 4Gi
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: LocalQueue
metadata:
  name: team-a
  namespace: default
spec:
  clusterQueue: training
YAML
```

Two CPUs on purpose: the point is to run out.

```bash
kubectl get clusterqueue training -o yaml | grep -A10 status # k9s: :clusterqueues, then y
kubectl get localqueue team-a                                # k9s: :localqueues
```

`namespaceSelector: {}` means every namespace may use this `ClusterQueue`. In 2.3 you will narrow
it, and that narrowing is the team boundary made real.

## Step 3 — submit a Job and watch admission happen

```bash
kubectl apply -f - <<'YAML'
apiVersion: batch/v1
kind: Job
metadata:
  name: probe-1
  namespace: default
  labels:
    kueue.x-k8s.io/queue-name: team-a
spec:
  suspend: true
  parallelism: 1
  completions: 1
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: sleep
          image: busybox:1.36
          command: ["sh", "-c", "sleep 120"]
          resources:
            requests:
              cpu: 1
              memory: 1Gi
YAML
```

Two things make this Job Kueue's business: `spec.suspend: true` and the label
`kueue.x-k8s.io/queue-name: team-a`. Without the label Kueue ignores it and it stays suspended
forever. Without the suspend Kueue has nothing to grant — the Job already started.

Now watch:

```bash
kubectl get workloads                                       # k9s: :workloads
kubectl get job probe-1 -o jsonpath='{.spec.suspend}{"\n"}'
kubectl get workload -o yaml | grep -A20 conditions         # k9s: :workloads, then y
kubectl get pods                                            # k9s: :pods
```

Read the `Workload` closely. Its name is derived from the Job, its `ownerReferences` point back at
the Job, and its conditions tell the story in order: `QuotaReserved`, then `Admitted`. The Job's
`spec.suspend` is now `false` — a field _you_ set that _Kueue_ changed. Pods exist only after that
flip.

## Step 4 — run out of quota, and read the refusal

```bash
kubectl apply -f - <<'YAML'
apiVersion: batch/v1
kind: Job
metadata:
  name: probe-2
  namespace: default
  labels:
    kueue.x-k8s.io/queue-name: team-a
spec:
  suspend: true
  parallelism: 2
  completions: 2
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: sleep
          image: busybox:1.36
          command: ["sh", "-c", "sleep 60"]
          resources:
            requests:
              cpu: 1
              memory: 1Gi
YAML

kubectl get workloads                                                  # k9s: :workloads
kubectl describe workload | sed -n '/Conditions/,$p'                   # k9s: select, then d
kubectl describe clusterqueue training | grep -A10 "Pending\|Admitted" # k9s: :clusterqueues, d
```

The second `Workload` has `QuotaReserved: False` with a message naming the exhausted resource. This
is the message your controller must surface in task 1.2's build half — a user whose job sits for an
hour needs to read "waiting for cpu quota in ClusterQueue training", not "Pending".

Notice what did **not** happen: no pod was created and failed, nothing was scheduled and evicted.
The refusal happened before any of that, which is the entire value of queueing ahead of scheduling.

## Step 5 — see who owns what

```bash
kubectl delete job probe-1
kubectl get workloads
```

The `Workload` for `probe-1` is gone, deleted by garbage collection, because Kueue made your Job its
owner. You will do the same thing in reverse: your `TrainingJob` becomes the owner of the Job it
creates, so deleting the `TrainingJob` removes the Job, which removes the `Workload`.

Clean up before part two:

```bash
kubectl delete job --all
kubectl delete localqueue team-a
kubectl delete clusterqueue training
kubectl delete resourceflavor default-flavor
```

Keep the YAML. Part two needs the queues back, and 2.3 turns them into real policy.

## The contract your controller must honor

From what you just watched, five rules fall out. They are the difference between a controller that
cooperates with Kueue and one that fights it.

1. **Create the Job suspended.** Creating it unsuspended means it starts immediately and quota means
   nothing.
2. **Label it into a `LocalQueue`.** The queue name comes from your `TrainingJob` spec, or from a
   per-namespace default you choose — not hardcoded.
3. **Never write `spec.suspend` after creation.** That field belongs to Kueue the moment the Job
   exists. A reconciler that re-applies its desired Job wholesale will set `suspend: true` again and
   un-admit a running job, repeatedly. This is the "never mutate another operator's resources beyond
   the fields you own" convention, and it is the most common way to break this task.
4. **Read, do not re-derive.** `Workload` conditions are Kueue's answer. Your status translates
   them; it does not recompute them.
5. **Own the Job.** One `ownerReference` from the child Job to the `TrainingJob`, so deletion
   cascades and no orphan survives a restart.

## Part two — the part that is yours

**You build:** the `TrainingJob` API and its reconciler.

1. **The API.** `kubebuilder create api --group ml --version v1alpha1 --kind TrainingJob`.

   The spec carries at least five things: the `Dataset` it trains on **by name**, the base model,
   the image, the resource request, and the queue. What each one is, which platform decision depends
   on it, and the two that are easy to get wrong — a dataset reference is a name and never an
   embedded object, and the image is pinned by digest rather than by tag — are in
   [domain.md](../product/domain.md#trainingjob), along with the fields that must stay out of the
   spec entirely.

   The resource request is the one that is a struct, and its fields are decided for you in
   [domain.md](../product/domain.md#specresources): `cpu` and `memory` as quantities, plus an
   optional `accelerator` naming a **class** and a **count**. Read the two paragraphs there on why
   the class is a platform word rather than `nvidia.com/gpu`, because that is the question this
   field exists to answer.

   In this task the accelerator half is **schema only**. Nothing on kind advertises a device, and
   the `AcceleratorClass` objects that resolve the name do not exist until
   [5.1](training-tasks.md#51-make-the-gpu-request-real-on-kind). A `TrainingJob` that sets
   `accelerator` should be refused with a condition that says the class is unknown — not silently
   rendered into a pod that will never schedule. Getting the field into the API now and resolving it
   later is deliberate: the shape of a spec is expensive to change once objects exist, and the
   resolution behind it is not.

   What makes them API fields rather than a web form is the constraints you put on them. All five
   are inputs, so a run whose inputs changed halfway through is not the run you audited: they are
   immutable after creation, which is the same webhook mechanism task 1.1 part two is about. Use
   validation markers for everything expressible as a marker — 0.3 taught that, and the review will
   check it. The queue is the one field worth defaulting rather than requiring, from a per-namespace
   choice you make.

2. **The reconciler.** Render one suspended `batch/v1` Job, owner-referenced, labelled into the
   `LocalQueue`, with `cpu` and `memory` landing in the pod template's `requests` where Kueue reads
   them — a request Kueue cannot see is a quota it cannot charge. Level-triggered: on every pass,
   read the child Job if it exists rather than assuming the last create succeeded, and do not
   re-apply fields Kueue owns.
3. **The translation.** Find the `Workload` for your Job and turn its conditions into platform
   vocabulary in `TrainingJob.status`: queued, admitted, running, succeeded, failed — with a reason
   that names the layer. "Quota exhausted in ClusterQueue training" and "image pull failed" are
   different sentences, and a user must not have to guess which one happened.
4. **The tests.** envtest for the rendering (one Job, suspended, owner-referenced, correctly
   labelled) and for the translation (given a `Workload` with `QuotaReserved: False`, the
   `TrainingJob` says so). Kueue's controller does not run in envtest, so you write the `Workload`
   yourself — which is exactly how you test the translation without a cluster.

**Acceptance criteria**

- A `TrainingJob` produces exactly one child Job, created suspended, owner-referenced, and labelled
  into a `LocalQueue`.
- Against the live cluster, Kueue admits it and the `TrainingJob` status reflects that without
  exposing Kueue's own condition names.
- With the `ClusterQueue` full, the status names quota as the reason, in a sentence a user who has
  never heard of Kueue can act on.
- Repeated reconciles do not change `spec.suspend` on an admitted Job. Prove it with a test that
  reconciles twice against an unsuspended Job.
- `make fmt vet test` passes.
